## 1. Сценарий S1 «стакан» (DoD §5.2) — бенчмарк последовательности инструментов (суррогатный)

Тест: `tests/SmetaNA.Core.Tests/S1CupScenarioBenchmarkTests.cs`
(`S1_CupToolSequence_RunsWithinBudget`).

**Бенчмарк суррогатный и не воспроизводит сценарий S1 целиком** (нахождение IM4):

* Заготовка — не брус 60×60×80 «с чистого листа»: `CupBlank()` строит брус
  с **предразрезанной** верхней гранью — контур бортика стенки 5 мм уже сформирован
  (строки 126–159 теста). В сценарии S1 этот контур пользователь рисует сам.
* «Настоящая» полость с вертикальными стенками текущими инструментами недостижима
  (расхождение ядра — ниже), поэтому последовательность шагов даёт полость
  с наклонными стенками и не равна результату S1.
* Сам критерий §5.2 («новичок за ≤ 15 минут») — юзабилити-замер (задача 6.6 плана,
  отложена 2026-10-27); здесь замерена только машинная стоимость последовательности
  инструментов на предразрезанной заготовке.

| Шаг | Инструмент и действие | Время, мс |
|---|---|---|
| 1 | Push/Pull: вдавливание полости −75 мм (дно 5 мм) | 23,1 |
| 2 | Push/Pull: подгонка дна +2 мм (дно 7 мм) | 0,16 |
| 3 | Окружность R20 мм: разметка дна | 35,1 |
| | **Сумма трёх шагов** | **58,36** |
| | **Итого (общий секундомер `total`)** | **63,2** |

* Строка «Итого» (63,2 мс) — отдельный секундомер на весь сценарий (строки 49 и 106
  теста): в него, кроме трёх шагов, попадают **промежуточные утверждения** — проверки
  watertight после шагов 1–2, сканирование уровня дна (`BottomZ`) и контроль геометрии
  вершин контура после шага 3. Разница 4,84 мс — стоимость этих проверок, а не времени
  инструментов (нахождение MN1 — объяснено, новых замеров не требует).
* Первый шаг включает прогрев JIT; устойчивое время шага Push/Pull на заготовке
  стакана подтверждается замером шага 2 — **0,16 мс** (тот же тест; нахождение M7
  аудит-цикла 2: прежняя ссылка «< 1 мс (см. §2)» некорректна — в §2 медиана коммита
  на меше ~50k составляет 4,7 мс, это другая сцена и другая граница замера).
  Бюджет теста — 2000 мс (страховка от регрессий, не норматив).
* После шагов 1–2 меш остаётся замкнутым (watertight), история — 3 команды,
  undo возвращает заготовку — всё проверяется в тесте.
* Замер — машина разработчика, Debug; на эталоне не подтверждён (см. шапку).

**Наблюдение (расхождение ядра):** рисование по грани
(`AddDrawingShapeCommand`) добавляет контур и грань поверх существующей, не
разрезая её (в отличие от SketchUp, где рисование по грани именно разрезает её),
а Push/Pull перемещает грань со склеиванием
вершин — «настоящая» полость с вертикальными стенками через инструменты пока
недостижима (шаг 1 даёт полость с наклонными стенками). Поэтому эталонные
модели для печати строятся API меша (§4), а шаги инструментами используются
для замера отклика. Задел — волна Core (разрезание граней/экструзия).

## 2. Отклик push/pull ≤ 16 мс (DoD §5.6) — на 500k НЕ ВЫПОЛНЯЕТСЯ

Тест: `tests/SmetaNA.Core.Tests/PushPullLatencyBenchmarkTests.cs`.

**Граница замера** (нахождение IM8): измеряемый цикл —
`MeshEditOps.PlanFaceMoveAlongNormal` + `Apply` + **`Revert`** (строки 118–123 теста):
путь коммита операции вместе с откатом замеренного переноса. Вне замера остаются:
наведение (замерено отдельно, строка 3 таблицы), перестройка render-модели сцены
(§6: `SceneRenderModel.Build` ~240 мс), перерисовка и вывод кадра. Полный путь отклика
«коммит → кадр» **не измеряется**; считать ли `Revert` частью норматива и что именно
есть «отклик push/pull» — методический вопрос, решение за владельцем (§9, п. 6).

| Сцена | Медиана | min | p95 | max | DoD ≤ 16 мс |
|---|---|---|---|---|---|
| Монолитный меш ~50k треугольников (`GridMesh(158)`: 24 964 квада, ~25k вершин) | **4,7 мс** | 3,7 | 5,3 | 5,6 | ✅ выполняется **на машине разработчика (Arc 140V, Debug)**; на эталоне не подтверждено |
| Монолитный меш 500k треугольников (`GridMesh(500)`: 250 000 квадов, 251 001 вершина в одном меше) | **38–76 мс** (по прогонам) | 36 | до 96 | до 107 | ❌ **НЕ выполняется** — превышение в 2–5 раз |
| Наведение (пик грани под курсором), тот же меш 500k | 136 мс | 126 | 168 | 191 | применимость бюджета ≤ 16 мс к наведению не определена (§9, п. 14); регрессионный бюджет теста 500 мс |

**Наименование сцены** (нахождение IM1): вторая строка — **не демо-сцена из §6**.
Тест строит **монолитный** меш `GridMesh(500)` — один меш на 251 001 вершину, тогда как
демо-сцена §6 (`DemoSceneFactory`) — 16 чанков по 15 876 вершин. Имя теста
(`PushPullCommit_DemoScene500k_WithinRegressionBudget`) вводит в заблуждение;
переименование теста — задача владельца кода (§9, п. 9). При равном числе треугольников
монолитный меш — более тяжёлый случай для склеивания: `PlanFaceMoveAlongNormal` обходит
вершины **одного** меша, и на чанковой сцене работа ограничилась бы вершинами чанка.

Выводы:

* **Бюджет DoD ≤ 16 мс на сцене 500k треугольников НЕ выполнен** (нахождение CR2):
  медиана коммита 38–76 мс — превышение в 2–5 раз. Это открытый критический долг
  (§9, п. 2); митигация — хеш/пространственный индекс позиций для glue-scope
  (владелец полосы Core — Granit; файлы Core вне полосы этого документа).
* **Зелёный тест ≠ выполнение DoD.** Тест
  `PushPullCommit_DemoScene500k_WithinRegressionBudget` проверяет медиану против
  **регрессионного бюджета** `HeavySceneRegressionBudgetMs = 250` мс (строки 31 и 67
  теста), а не против `DodBudgetMs = 16` (строка 23): порог 250 мс фиксирует текущий
  уровень, чтобы набор не краснел. Норматив DoD ≤ 16 мс на 500k не подтверждается
  никаким тестом и отслеживается только этим отчётом.
* **Для моделей порядка десятков тысяч треугольников** (типовой размер модели
  школьного проекта/корпуса) цель ≤ 16 мс выполняется — на машине разработчика
  в Debug; на эталонной конфигурации не подтверждено.
* Причина превышения на 500k: перенос со склеиванием проходит по **всем** вершинам
  меша (`MeshEditOps.PlanMove`, glue-scope = весь меш), стоимость O(N) на каждый
  коммит.
* Наведение (пик лучом по всем граням `SceneFacePicker`) на 500k — ~136 мс;
  в UI наведение троттлится до 25 Гц, но крупные сцены ощутимо деградируют.
  Распространяется ли норматив «отклик ≤ 16 мс» (DoD §5.6) на наведение — нигде
  не определено; вопрос отслеживается отдельно от коммита (§9, п. 14; нахождение M8
  аудит-цикла 2). Митигация — BVH/пространственный индекс для пиккинга (задел Core).
* Регрессионные бюджеты теста: 16 мс на ~50k (`DodBudgetMs`), 250 мс на 500k
  (`HeavySceneRegressionBudgetMs`), 500 мс наведение (`HoverBudgetMs`).

## 3. Точность 0,01 мм (DoD §5.4) — сверка

Относящиеся к критерию тесты существуют и прогон зелёный, но **покрытие норматива
неполное** — квалификация в итоге раздела (нахождение I1 аудит-цикла 2). **Что именно
покрывает каждый набор** (нахождение IM6, сверено с кодом 2026-11-24):

* `tests/SmetaNA.Formats.Tests/RoundTripTests.cs` — round-trip экспорт→импорт
  **golden-мешей** `GoldenMeshes`: куб 100×100×100 (1 000 000 мм³);
  **прямоугольный** стакан 60×60×80, стенка 5, дно 5 (100 500 мм³); подставка —
  ступенька габаритом 100×60×50 (база 100×60×20 + верх 60×60×30, 228 000 мм³).
  Куб и стакан геометрически **не совпадают** с эталонными моделями §4 (стакан §4 —
  вписанная призма, а не прямоугольный ящик); golden-подставка по габаритам и объёму
  **совпадает** с эталонной подставкой §4 (та же ступенька 100×60×20 + 60×60×30),
  различие только в происхождении: golden-меши заданы фиксированными массивами
  вершин в `GoldenMeshes.cs`, модели §4 строятся через `ReferenceModelFactory`.
  Форматы — все четыре (`BinaryStl`, `AsciiStl`, `Obj`, `ThreeMf`). Допуски: углы —
  **0,01 мм** (`MeshAssert.EqualCorners`), объём — **1 %**; после импорта проверяется
  печатаемость. Габаритная проверка (100 мм) и дюймовые единицы покрыты
  `[InlineData]` только для `BinaryStl`/`AsciiStl`/`Obj` — **3MF в этих двух проверках
  не участвует**.
* `tests/SmetaNA.Formats.Tests/ReferenceModels/ReferenceModelExportTests.cs` —
  эталонные модели §4: `ExportRoundTrip_KeepsGeometryWithinDodTolerance` во всех
  **9 комбинациях «модель × формат»** (3 модели × `BinaryStl`/`Obj`/`ThreeMf`):
  углы — **0,01 мм**, объём — 1 %; `ReferenceModel_VolumeMatchesAnalyticFormula` —
  объём против аналитической формулы модели (допуск **0,1 %**; для стакана формула —
  192-угольная призма после SMET-2, см. §4); `CommittedFixture_MatchesFactoryModel` — сверка
  закоммиченных файлов с фабрикой (0,01 мм).
* `tests/SmetaNA.Core.Tests/ScaleToDimensionTests.cs` — масштабирование модели
  по заданному размеру с точностью ≤ 0,01 мм (задача 3.2);
* `tests/SmetaNA.Core.Tests/DimensionMathTests.cs` — разрядность/точность
  размерного текста (DoD §5.4).

Итог (квалификация по находке I1 аудит-цикла 2 и решению владельца 2 от 2026-11-24):
допуск углов 0,01 мм в обоих наборах покрывает норматив §5.4 **для операций, не
завязанных на аппроксимацию цилиндра** — round-trip golden-мешей, масштабирование,
размерный текст. **По эталонной модели стакана DoD §5.4 может считаться покрытым
при условии интеграции ветки `agent/kontur/smet-2` в `release/0.1.0-beta`**: задача
SMET-2 (коммит `ab8831e`) увеличила сегментность стакана до n = 192, и фактические
отклонения от цилиндра Ø60 уложились в допуск 0,01 мм по обеим метрикам (§4:
диаметральное отклонение 0,008032 мм, радиальная стрелка 0,004016 мм). На момент
ревизии v4 (2026-11-24) ветка **не слита**: в `release/0.1.0-beta` фактическим
остаётся прежнее состояние (n = 48, диаметральное отклонение 0,1285 мм, стрелка
0,0642 мм — вне допуска), поэтому §5.4 по стакану объявляется покрытым только
после слияния; трекинг — §9 п. 13 (ожидает интеграции, владелец — pull request).
Допуск объёма 1 % в round-trip — более грубая страховка от поломок экспорта/импорта,
не часть норматива §5.4.

## 4. Эталонные модели (DoD §5.3, задачи 4.6 и S3)

Программируемые фикстуры через API меша:
`tests/SmetaNA.Formats.Tests/ReferenceModels/ReferenceModelFactory.cs`
(параметры: габариты, толщина стенки/дна, размер выреза; единицы — мм).

| Модель | Габариты (по умолчанию) | Объём, мм³ | Особенности |
|---|---|---|---|
| Стакан (`cup`) | габарит 60×60×80, стенка 5, дно 5 | 78 918,4 | **не цилиндр**: вписанная 192-угольная призма (SMET-2, см. ниже) |
| Подставка (`stand`) | база 100×60×20 + верх 60×60×30 | 228 000 | ступенька |
| Корпус (`enclosure`, S3) | 100×80×40, стенка 4, дно 4 | 80 384 | открыт сверху; окно 24×12 в передней стенке, Z от 16 до 28 |

**Геометрия стакана** (нахождение IM3; числа — фактические результаты задачи SMET-2,
коммит `ab8831e`, ветка `agent/kontur/smet-2`): стакан строится как **192-угольная
призма**, вписанная в цилиндр Ø60 (`segments = 192`), а не аналитический цилиндр:

* Объём **78 918,4276 мм³** (из `cup.obj`) при аналитическом объёме цилиндра Ø60×80
  со стенкой 5 и дном 5 **78 932,515 мм³** (π·30²·80 − π·25²·75): расхождение
  **−0,0178 % (−14,09 мм³)**, в допуске теста 0,1 %. Формула теста —
  `PolygonArea(192, 30)·80 − PolygonArea(192, 25)·75`
  (`ReferenceModel_VolumeMatchesAnalyticFormula`): допуск «0,1 % к аналитическому»
  по-прежнему относится к **призме**, а не цилиндру, — prism-аппроксимация занижает
  аналитический объём, при n = 192 всего на ~0,018 % (при n = 48 было ~0,29 %).
* Отклонение от цилиндра Ø60 (терминология — по находке M2 аудит-цикла 2):
  **радиальная стрелка** (хордовое отклонение, R·(1 − cos(π/192))) — **0,004016 мм**;
  **диаметральное отклонение** — **0,008032 мм**: размер «по плоскостям»
  192-угольника 2·30·cos(π/192) = **59,99197 мм** против Ø60. **Обе метрики
  укладываются в глобальный допуск 0,01 мм** (DoD §5.4). Габаритная коробка (AABB) —
  ровно **60,000000 × 60,000000 × 80,000000 мм**: вершины описанной окружности
  ориентированы по осям (192 кратно 4, экстремумы по X/Y попадают точно на оси),
  поэтому габаритная проверка слайсеров (§5, шаг 6) проходит; сечение детали
  остаётся многоугольным, но отклонение от окружности теперь в пределах допуска.
* Размер меша: треугольники 384 → **1536**, вершины 194 → **770** (до → после
  SMET-2).

**Результат SMET-2 (решение владельца 2 от 2026-11-24, находка I1 аудит-цикла 2).**
Вариант «закрепить номинал "48-угольная призма"» отклонён; принято **увеличить
сегментность** эталонного стакана так, чтобы отклонение от цилиндра Ø60 уложилось
в допуск 0,01 мм по обеим метрикам. Правка выполнена в задаче **SMET-2** (полоса
Kontur: код `ReferenceModelFactory`, фикстуры `cup.*` перегенерированы; коммит
`ab8831e`, ветка `agent/kontur/smet-2`). Подтверждение получено: `dotnet build`
чист, `Formats.Tests` 203/203, `Core.Tests` 583/583 (проверено оркестратором);
числа выше — **фактические**, пометка «ожидается подтверждение прогоном» снята.
**Условие действия этих чисел — интеграция ветки `agent/kontur/smet-2` в
`release/0.1.0-beta`**: на момент ревизии v4 (2026-11-24) ветка не слита,
трекинг — §9 п. 13 (ожидает интеграции, владелец — pull request).

**Историческое состояние до SMET-2** (n = 48; сохранено, поскольку оно объясняет,
почему §3 в ревизиях v2–v3 не мог объявить DoD §5.4 покрытым по стакану): объём
**78 707 мм³**; размер «по плоскостям» 48-угольника 2·30·cos(π/48) = **59,8715 мм** —
**диаметральное отклонение 0,1285 мм** относительно Ø60; хордовое отклонение
(стрелка, R·(1 − cos(π/48))) вдвое меньше — **0,0642 мм**. **Обе метрики превышали
глобальный допуск 0,01 мм** (DoD §5.4) в сечении. В ревизии v2 (и в отчёте

## 6. FPS вьюпорта на демо-сцене 500k (DoD §5.6)

Демо-сцена: `DemoSceneFactory` — 16 чанков рельефа (125×125 квадов на чанк,
15 876 вершин), ровно **500 000 треугольников** (каждый квад → 2 треугольника).
Число «504 000 рёбер» из прежней ревизии — **render-рёбра** 16 чанковых мешей
(поле `edges=` строки `[VIEWPORT]`; `SceneRenderModel.EdgeCount` — сумма
`RenderObject.EdgeCount` по объектам): рёбра квад-сетки без диагоналей триангуляции,
2·125·126 = 31 500 на чанк × 16 = 504 000 (нахождение MN3 — определено). Это **не**
топологические рёбра единого меша 500k из §2.

С 2026-10-27 (задача 6.0) рельеф не сеется при старте. **При обычном запуске сцена
пустая**: `SeedStartScene` без флагов завершается досрочно (метод —
`MainWindowViewModel.cs` строки 743–763, защита `if (App.Smoke is null)` — строки
755–758; нахождение M4 аудит-цикла 2 — диапазон строк уточнён); лёгкая эталонная
сцена (`ReferenceSceneFactory.AddToScene`) сеется **только в смоук-режиме**
(`--smoke`), демо-рельеф 500k — **только по флагу `--demo-terrain`** (нахождение IM2 —
исправлено; прежняя формулировка «стартует лёгкая эталонная сцена» коду не
соответствовала). Ветки засева **взаимоисключающи**: ветка `--demo-terrain` выходит
из `SeedStartScene` через `return` (строка 752) до проверки смоука, поэтому
в замерном прогоне (`--smoke` + `--demo-terrain` одновременно) сцена содержит
**только** рельеф 500k — лёгкая эталонная сцена к нему не добавляется, и счёт
«ровно 500 000 треугольников» для прогонов §6 сохраняется (нахождение M1
аудит-цикла 2 — **отклонено по коду**: `SeedStartScene`, строки 743–763).

Замер — GUI-прогон с отключённым лимитом кадров (12 с, свой frame pacing
выключен): `SmetaNA.EditorUI.exe --smoke 12 --fps 0 --demo-terrain [--wgl]`, строка
`[VIEWPORT]`. Строка 3 таблицы — тот же прогон ANGLE с зоной печати, включённой
**вручную** (палитра → «Зона печати» → «Показать зону»; CLI-флага у зоны нет).
Конфигурация всех строк — машина разработчика, Debug.

| Режим GL | Средний FPS | Мин. FPS | Последний кадр, мс | Примечание |
|---|---|---|---|---|
| ANGLE (D3D11), дефолт | **140,1** | 135,1 | 6,87 | Intel Arc 140V, Debug |

**Семантика столбцов** (нахождение MN2 — объяснено; имена членов кода исправлены по
нахождению M3 аудит-цикла 2): столбцы не обязаны быть обратными
друг другу. `Средний FPS` = (число кадров − 1) / длительность прогона между первым
и последним кадром (свойство `GlViewportControl.AverageFps`, строка 254);
`Мин. FPS` = минимум по односекундным бакетам после прогрева 2 с (свойство
`GlViewportControl.MinFps`, строка 264; минимум бакета — поле `MinBucketFps`
record-типа `ViewportStats`, строка 19); `Последний кадр, мс` =
время **последнего кадра прогона** (поле `GlViewportControl._frameMs`, строки 62
и 574, `frameMs = dt·1000` в `UpdateStats`) — мгновенный
отсчёт, а не среднее. Поэтому 6,87 ≠ 1000/140,1 = 7,14, а в строке 3 «среднее время
кадра» (13,73) некорректно сравнивать с 1000/мин.FPS — это разные статистики.
Среднее время кадра, обратное среднему FPS: 7,14 / 12,77 / 13,05 мс.

**Примечание к строкам 2 и 3** (нахождение M9 аудит-цикла 2, прогоном не
подтверждено): минимальный FPS в них совпадает (73,5) при разных средних и
последних кадрах — возможно дублирование значения. Логи прогонов, по которым снята
таблица, не сохранены, поэтому сверить значение без пересъёма невозможно; проверка
включена в состав Release-пересъёма (§9, п. 10).

* Цель DoD ≥ 30 FPS **выполняется на машине разработчика** (Windows 11, Intel Arc
  140V, Debug) во всех режимах; **не подтверждено на эталонной минимальной

* Укладка в 8 ГБ RAM не контролировалась (не измерялась ни в одном прогоне).
* Подсветка «за пределами зоны» на сцене, где вне зоны все 500k треугольников
  (нехарактерный случай для печати), по средним FPS стоит **≈5,92 мс/кадр**

## 7. Как повторить замеры

Команды используют `dotnet` из PATH. **Расхождение среды (нахождение I3
аудит-цикла 2; закрыто решением владельца 4 от 2026-11-24 — зафиксировать
фактическую среду, замеры не переснимать):** замеры сняты на **SDK 10.0.402** —
версии, установленной на машине разработчика в момент снятия замеров; закрепление
в `global.json` появилось **после** замеров (коммит репозитория `a265cc5`:
SDK **10.0.404**, `rollForward: latestFeature`, `allowPrerelease: false`).
Согласно официальной документации .NET
(`learn.microsoft.com/en-us/dotnet/core/tools/global-json`), `latestFeature`
использует старшую установленную feature band и patch level, **соответствующие
запрошенным major и minor**, при значении не ниже указанного; если таких нет —
завершается ошибкой. То есть политика **не пересекает границу major/minor** —
для этого нужен `latestMajor`. На машине, где установлен только 10.0.402,
предписанные команды **не выполнятся**; отдельно установленный SDK 11.x
закрепление 10.0.404 при `latestFeature` также **не** удовлетворит. Для
воспроизведения требуется **стабильный SDK ветки 10.0 не ниже 10.0.404**; числа
этого документа соответствуют фактической среде замеров (10.0.402) и пересъёму
не подлежат. Прежняя ревизия
указывала персональный путь `C:\Users\mnk\.dotnet\dotnet.exe` — он зависит от
окружения машины и частью методики не является (нахождение MN5). Прогоны — в
**Debug** (умолчание `dotnet test` и путь `bin/Debug` ниже); для закрытия DoD
повторить в Release (§9, п. 10).

