## 1. Модель продажи

- **Продукт:** персональная бессрочная лицензия на smetana (разовая покупка) + 12 месяцев обновлений. Модель подписки спекой не выбрана (§7: «решить позже») — контракты ниже адаптируются под подписку (у ЮKassa и CloudPayments есть автоплатежи).
- **Триал:** 14 дней без оплаты (`TrialOptions.Length`, локально, без сети).
- **Активация:** после оплаты покупатель получает письмо с лицензионным ключом; активация — офлайн, в приложении (токен + node-lock + лимит активаций, см. `SmetaNA.Licensing`). VPN не нужен (DoD §5.8).
- **Тарифы (плейсхолдеры — цены утверждать до старта продаж, спека §7):**

| Тариф | Что входит | Лимит активаций | Цена |
|---|---|---|---|
| Личная | smetana v1.x, 12 мес обновлений, 1 пользователь | 2 привязки к устройствам в год (перенос/деактивация) | TBD ₽ |
| Личная + (семья/студент) | то же, до 3 устройств | 6 привязок в год | TBD ₽ |
| Учебная (класс/аудитория) | сетевые/floating-ключи | — | **v1.x** (спека §7: в MVP только личные ключи) |

## 2. Платёжные провайдеры (все — РФ, 54-ФЗ)

| Провайдер | Роль | Почему подходит (R4) |
|---|---|---|
| **ЮKassa** | основной | ККТ и электронные чеки 54-ФЗ из коробки, карты РФ/СБП, автоплатежи (для подписки в v1.x), sandbox |
| **CloudPayments** | основной (параллельно) | облачная касса 54-ФЗ, сервис подписок/автосписаний, виджет, тестовый режим |
| Робокасса | запасной | redirect-форма, широкий набор способов оплаты, простая интеграция |
| Т-Банк (эквайринг) | запасной | эквайринг для ИП/ООО в РФ, чеки через их кассу |

Stripe/Paddle и прочие зарубежные провайдеры не используются для РФ-продаж (санкции; см. спека §4). Продажи за рубеж — отдельным треком через MoR-посредника (спека §7, остаточная задача).

## 3. 54-ФЗ: чеки

Оплата на сайте — электронная, значит чек выдаётся **в электронном виде** на email (или телефон) покупателя одновременно с расчётом (54-ФЗ, ст. 1.2). Схема:

1. При создании заказа покупатель указывает **email** (обязателен для чека) и соглашается с EULA/privacy ([legal/](legal/)).
2. Данные чека передаются агрегатору в момент оплаты (он же — облачная ККТ и ОФД-партнёр; расчёт «через платёжного агрегатора»):
   - **признак предмета расчёта** — «услуга» / «программное обеспечение» (точное значение согласовать с бухгалтером);
   - **способ расчёта** — «полный расчёт» (для полной предоплаты);
   - **номенклатура** — «Лицензия smetana <тариф>, версия 1.x»;
   - **ставка НДС** — зависит от СНО (УСН «доходы» — «не облагается»; ОСНО/УСН с НДС — 20%) — **уточнить у бухгалтера до продаж**;
   - **сумма, количество** — из тарифа; валютный код RUB.
3. Возврат — через API провайдера (refund) + кассовый чек возврата; лицензия отзывается (см. §6).

Таким образом кассовый аппарат продавцу не нужен: чеки печатает касса агрегатора. Реквизиты организации/ИП (ИНН, наименование, СНО) указываются в личном кабинете агрегатора.

## 4. Внутренний API-контракт интеграционного слоя

Backend-сервис «Заказы и лицензии» (будущий, размещается на хостинге в РФ). REST/JSON, HTTPS, версия контракта `/api/v1`. Все суммы — строки вида `"1990.00"`, валюта `RUB`.

### 4.1. Создание заказа

`POST /api/v1/checkout` — вызывает [site/buy.html](../site/buy.html) (форма покупки).

```json
// запрос
{
  "tariffId": "personal",            // personal | personal-3
  "email": "buyer@example.ru",       // для чека 54-ФЗ и доставки ключа
  "name": "Иван",                    // добровольно
  "locale": "ru",                    // ru | en
  "acceptEula": true,                // обязательно true
  "acceptPrivacy": true              // обязательно true
}

// ответ 201
{
  "orderId": "ord_01H...",
  "provider": "yookassa",            // yookassa | cloudpayments | robokassa | tinkoff
  "paymentUrl": "https://yookassa.ru/...",  // редирект/виджет оплаты
  "amount": "1990.00",
  "expiresAt": "2026-10-23T20:00:00+03:00"
}
```

Ошибки: `400` (валидация, нет согласий), `409` (заказ уже оплачен), `502` (провайдер недоступен — показать «попробовать позже», **не** терять заказ).

### 4.2. Статус заказа и получение ключа

`GET /api/v1/orders/{orderId}` → `{ "orderId", "status": "pending|paid|failed|refunded", "licenseKey": "…", "email": "…" }`.

`licenseKey` возвращается **только в статусе `paid`** и только покупателю (страница успеха + письмо). Повторные обращения идемпотентны (ключ стабилен).

### 4.3. Вебхуки провайдеров

| Endpoint | События | Авторизация |
|---|---|---|
| `POST /api/v1/webhooks/yookassa` | `payment.succeeded`, `payment.canceled`, `refund.succeeded` | доверяем только IP ЮKassa + **обязательная перепроверка статуса через API** (`GET /v3/payments/{id}`) перед выдачей ключа |
| `POST /api/v1/webhooks/cloudpayments` | `check`, `pay`, `fail`, `refund` | HTTP Basic (`PublicId : API Secret`), `check` — синхронная проверка возможности списания |
| `POST /api/v1/webhooks/robokassa` | `Result URL` | `SignatureValue = MD5(MerchantLogin:OutSum:InvId:Secret)` |
| `POST /api/v1/webhooks/tinkoff` | `PaymentNotify` | HMAC от `Password` терминала |

Правило для всех: **вебхук — только сигнал**; источник истины — запрос статуса к API провайдера (или проверка подписи), затем выдача ключа ровно один раз (идемпотентность по `orderId`).

### 4.4. Выдача лицензии (внутренний шаг)

После подтверждённой оплаты: сгенерировать `LicenseKey` (подпись закрытым ключом продавца, `SmetaNA.Licensing`) на email покупателя и отправить письмо с ключом и ссылкой на [инструкцию активации](../site/activation.html). Отмена/возврат платежа → `ActivationTokenIssuer.Revoke(...)` + отзыв в ближайшем `RevocationList` (поставляется с обновлениями v1.x).

### 4.5. Конфигурация (секретов в репозитории нет)

```
# .env сервиса (пример, значения не коммитить)
YOOKASSA_SHOP_ID=...
YOOKASSA_API_KEY=...
CLOUDPAYMENTS_PUBLIC_ID=...
CLOUDPAYMENTS_API_SECRET=...
ROBOKASSA_LOGIN=...
ROBOKASSA_PASS1=...          # только серверная подпись
TINKOFF_TERMINAL_KEY=...
TINKOFF_PASSWORD=...
LICENSE_SIGNING_KEY_PATH=... # закрытый ключ выдачи лицензий (HSM/файл с правами 600)
PUBLIC_BASE_URL=https://smetana.example.ru
```

## 5. Sandbox / тестовые режимы (без реальных денег)

| Провайдер | Режим | Как тестировать |
|---|---|---|
| **ЮKassa** | Тестовый режим (вкладка «Тестовый режим» личного кабинета; отдельные тестовые shopId/API-ключ) | карты `5555 5555 5555 4444` (3-D Secure), `5555 5555 5555 4477` (отказ); сценарии успех/отмена/ожидание 3-D Secure; тестовые вебхуки |
| **CloudPayments** | Test API (PublicId `test_api`, без боевого секрета) | карта `4111 1111 1111 1111` (успех), `4242 4242 4242 4242` (отказ); панель тестовых событий для вебхуков `check`/`pay`/`fail` |
| Робокасса | тестовый магазин (`Login_test`/`Pass1_test`) | Success/Fail/Result URL на тестовый backend |
| Т-Банк | тестовый терминал (Pay-форма demo) | тестовые карты банка |

Порядок прогона e2e (sandbox): форма покупки → `checkout` → оплата тестовой картой → вебхук → `GET /orders/{id}` → ключ получен → ввод ключа в приложение → офлайн-активация. **Реальные ключи провайдеров и ключ выдачи лицензий в репозиторий не попадают.**

## 6. Безопасность и откаты

1. Ключ выдачи лицензий — только на backend (никогда в клиенте/сайте).
2. Идемпотентность выдачи ключа по `orderId`; повторный вебхук не выдаёт второй ключ.
3. Антифрод-минимум: лимит попыток оплаты на email, проверка суммы из тарифа на сервере (не доверяем клиенту), лог операций без персональных данных сверх необходимости.
4. Возврат платежа → отзыв лицензии (`ActivationTokenIssuer.ProcessDeactivation`/`Revoke`) и публикация в `RevocationList` (с обновлениями).
5. Вебхуки — только HTTPS, проверка подписи/Basic/HMAC (§4.3), игнорирование чужих IP.

## 7. Что сделать до старта продаж (см. спека §7)

1. Утвердить тарифы и цены (заготовки — §1).
2. Выбрать провайдера (рекомендация: ЮKassa + CloudPayments параллельно), заключить договор, получить боевые ключи.
3. Определить СНО и ставку НДС для чека (§3), реквизиты — в личный кабинет агрегатора.
4. Реализовать backend «Заказы и лицензии» по контракту §4 (вне этого репозитория), поднять на хостинге в РФ (R4).
5. Подключить форму [site/buy.html](../site/buy.html) к `POST /api/v1/checkout` (заглушка `site/assets/buy.js` показывает ожидаемый поток).
6. Прогнать sandbox e2e (§5), включая возврат и отзыв лицензии.
7. Проверить формулировки EULA/privacy с юристом (возвраты цифрового товара, согласия, 152-ФЗ).
