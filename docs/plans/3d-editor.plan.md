# SmetaNA — план работ до v1.0

- **Статус:** черновик плана (спека утверждена 2026-10-22)
- **Основание:** [спека 3d-editor.spec.md](../specs/3d-editor.spec.md), исследования [01](../research/01-sketchup-analysis.md) / [02](../research/02-3d-systems-overview.md) / [03](../research/03-stack-licensing.md)
- **Команда:** один разработчик (координатор); оценки — в человеко-неделях (чел/нед), календарный срок зависит от занятости; вариант исполнения делегированными чатами — §5
- **Пересмотр оценок:** каждые 3 месяца или по завершении фазы

---

## 0. Рамки и стратегия

**Рамки:** Windows 10/11 + Linux x64; стек — C# / .NET 10 LTS + Avalonia 12 + Silk.NET (OpenGL) + Manifold (см. спека §4); MVP закрывает оба направления равнозначно (3D-печать + промышленный дизайн); минимальная конфигурация — 8 ГБ RAM / Intel UHD 620.

**Стратегия:**

1. **Сначала «сердце» UX.** Push/Pull и inference-привязки — то, за что любят SketchUp. Их нельзя откладывать на конец: это ядро архитектуры и главный риск.
2. **Вертикальные срезы.** Каждая фаза завершается работающим приложением с видимым результатом, а не «библиотекой без UI».
3. **Геометрия — под тестами с первого дня.** Golden-меш тесты экспорта, фузи-тесты CSG, валидатор watertight (риск R2 из спеки).
4. **Ранние спики рисков.** Manifold C API + GL-вьюпорт в Avalonia проверяются в фазе 0 до масштабных вложений.
5. **Ранний публичный выход.** Альфа после фазы 2, бета после фазы 4 — защита от «вечной стройки» (риск R1/R8).

## 1. Фазы

### Фаза 0 — Каркас и проверка рисков · 2–3 чел/нед

| Задача | Описание |
|---|---|
| 0.1 | Репозиторий, решение .NET 10, структура проектов: `Core` (сцена/меш), `Rendering`, `EditorUI`, `Formats`, `Licensing`, тесты |
| 0.2 | CI: сборка Win + Linux, юнит-тесты, smoke-запуск; editorconfig + анализаторы; SBOM/инвентаризация лицензий |
| 0.3 | **Spike GL:** окно Avalonia с OpenGL-вьюпортом (Silk.NET) — вращаемый куб, FPS-счётчик, на Win и Linux |
| 0.4 | **Spike Manifold:** тонкий слой над C API (`MANIFOLD_CBIND`) — булева операция на тестовых мешах, замер производительности |
| 0.5 | Каркас undo/redo и структуры данных сцены (проектирование, без реализации инструментов) |

**Результат:** запускаемое приложение на обеих ОС, CSG через Manifold работает из C#.
**Критерий выхода:** оба спика зелёные. **Иначе — возврат к альтернативам спеки §4** (пересборка стека на ранней стадии, пока цена переключения мала).

## 3. Дорожная карта v1.x (после релиза, порядок — по ценности)

1. **M6-хвост:** Shell (оболочка с толщиной стенки — корпуса под печать), Fillet/Chamfer, полный Solid Tools, лофт.
2. **M8-развитие:** анализ толщины стенок, автоисправление мешей, разбиение на части, импорт SKP→OBJ (перенос из SketchUp).
3. **M4-развитие:** «живые размеры» (правка числа перестраивает геометрию), угловые/радиальные размеры, 2D-документация PDF/DXF по ЕСКД.
4. **M5-развитие:** библиотеки компонентов во внешних файлах, сборочные Snaps.
5. **M7-развитие:** текстуры, стили отображения, сцены, тени, секущие плоскости, экспорт glTF и изображений.
6. **M10-развитие:** интерактивные уроки, палитра команд, шаблоны-задания для учителей.
7. **M11:** публичный API плагинов (C#-скриптинг) → позже маркетплейс.
8. **M12-развитие:** автообновления, учебные/сетевые (floating) лицензии для классов.
9. **v2 (кандидаты):** параметрическое дерево/история, B-rep-модуль (OCCT, см. спека §4), macOS, Snaps-сборки.

## 4. Ритм работы

- Итерации по 2 недели; в конце каждой — работающий результат (демо), а не отчёт о процентах.
- Трекинг задач — по мере выполнения фаз детализируются в задачи; каждая задача завязана на модуль M* и пункт DoD из спеки.
- Метрики на каждой итерации: FPS на эталонной сцене, отклик push/pull, время сценария S1, закрытые пункты DoD.
- Пересмотр плана: по завершении фазы 2 (самой рискованной) и каждые 3 месяца.

## 5. Параллельная работа делегированными чатами (вариант исполнения)

План выше рассчитан на одного разработчика, но календарь фаз можно сжать параллельной работой делегированных чатов (автономных сессий в изолированных worktree). Объём работ (чел/нед) не уменьшается — сжимается календарь за счёт боковых треков. Границы модулей из задачи 0.1 (`Core`, `Rendering`, `EditorUI`, `Formats`, `Licensing`, тесты) — готовые границы владения для чатов.

**Что параллелится:** спики 0.3/0.4 между собой; `Formats` (4.2–4.4 с golden-меш тестами) — против API меш-ядра; `Licensing` (6.4) — полностью автономно; каркас UI (6.1–6.3) — против мок-инструментов; inference (2.4–2.6) — отдельно от инструментов при замороженном контракте запроса привязок; фазы 3 и 5 — между собой (разные подсистемы).

**Что не параллелить:** меш-ядро (1.1) и push/pull + stickiness (2.2) — единый блок; финальную интеграцию, юзабилити-тест и прогон DoD (6.6–6.7) — одной рукой. «Сердце» (фаза 2) дробится только по замороженному API inference; остальное — плотная координация.

**Волны:**

| Волна | Параллельные чаты | Примечание |
|---|---|---|
| 0. Фундамент (сериально, 1–2 нед) | 0.3 спик GL ∥ 0.4 спик Manifold | git init + 0.1 + 0.2 + заморозка контрактов 0.5 (меш/сцена, undo/redo, запрос привязок, форматы) |
| 1. Боковые треки | A: фаза 1 (ядро + вьюпорт) ∥ B: 4.2–4.4 ∥ C: 6.4 ∥ D: каркас 6.1–6.3 | B/C/D — против контрактов и мок-инструментов |
| 2. Сердце (фаза 2) | 2.1 ∥ 2.3 ∥ 2.4–2.6; 2.2 — единым блоком | самая рискованная фаза; VCB (2.5) стыкуется с треком D |
| 3. Расширение | фаза 3 ∥ фаза 5 ∥ достройка фазы 4 (4.1, 4.5–4.6) | |
| 4. Интеграция (фаза 6) | 6.5 (платежи, сайт) ∥ сериально 6.1–6.7 | юзабилити-тест и прогон DoD — одной рукой |

**Правила делегирования:**

1. git-репозиторий обязателен до запуска параллельных чатов: изоляция worktree без git невозможна, иначе чаты затирают правки друг друга.
2. Владение файлами: каждый чат — свои директории; общие файлы (solution/csproj, контракты) правит только координатор.
3. Контракты волны 0 замораживаются; их изменения — только координатором.
4. Единый контур качества: editorconfig + анализаторы (0.2) — до параллелизма; каждый чат завершает задачу прогоном своих тестов, координатор — полным сьютом после merge.
5. Мелкие merge после каждой задачи; сверка на границах итерации (2 недели). Интеграционный чек-лист координатора: прогнать `fetch-native.ps1` (Manifold, lib3mf) → добавить новые проекты в решение → полный сьют.

**Ожидаемый эффект:** календарное сжатие ориентировочно на 30–45% (≈6–8 мес вместо 9–13 при полной занятости). Критический путь (волна 0 → ядро → фаза 2 → интеграция) почти не сжимается; контрольные точки §2 остаются обязательными, чтобы параллелизм не превратился в «вечную стройку» (R1).

## 6. Риски плана

| Риск плана | Реакция |
|---|---|
| Spike фазы 0 провалился (GL в Avalonia / Manifold C API) | Пересборка стека по альтернативам спеки §4 — цена переключения минимальна |
| Фаза 2 затягивается > 16 чел/нед | Урезание M2-хвоста в v1.x; push/pull + inference не трогаем |
| Соло-выгорание (R8) | Публичная альфа после фазы 2, видимый прогресс каждые 2 недели, честный scope |
| Выход за бюджет 53 чел/нед | Сокращение фазы 5 (массивы/зеркало → v1.x) и хвоста фазы 6 (уроки → v1.x); ядро, точность, печать не режем |
| Параллельные чаты: конфликты слияний, расхождение стилей, интеграционный долг | Правила §5: файловое владение, замороженные контракты волны 0, анализаторы до параллелизма, мелкие merge и полный прогон тестов координатором |
